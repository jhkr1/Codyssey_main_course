## 재현 가이드 (실행 방법)

이 프로젝트를 로컬 환경에서 실행하고 테스트하기 위한 방법입니다.

```bash
# 1. 가상환경 생성
python3 -m venv venv

# 2. 가상환경 활성화
```

서버가 기동되면 웹 브라우저에서 `http://127.0.0.1:8000/`로 접속하여 나의 메모 앱을 확인하실 수 있습니다.

## 1장. 미션 개요
본 미션은 FastAPI와 SQLAlchemy를 활용하여 웹 애플리케이션의 핵심 구성 요소를 직관적인 구조로 설계하는 프로젝트이다. 단순한 기능 구현을 넘어, 라우터, 서비스, 저장소로 역할을 분리하고 PRG 패턴과 ORM을 적용하여 유지보수가 가능한 웹 서비스를 구축하는 것을 목표로 한다.

비유하자면 이 프로젝트는 **'대형 레스토랑 주방 시스템'**을 설계하는 것과 같다. 주문을 받는 웨이터가 모든 요리를 다 할 수는 없다. 역할을 명확히 분리해야 시스템 전체가 무너지지 않고 확장할 수 있다.

비전공자 관점에서는 "모든 코드를 한곳에 넣으면 나중에 수정할 때 다 엉킨다"는 점만 기억하면 된다.

## 2장. 학습 목표
- [ ] 브라우저 요청이 "라우터 → 서비스 → 저장소 → 템플릿"으로 흐르는 과정을 설명할 수 있다.
- [ ] GET과 POST의 역할 차이를 이해하고 적절한 상황에 구분하여 사용할 수 있다.
- [ ] 폼 입력값이 서버로 전달되어 처리되는 데이터 바인딩 과정을 이해한다.
- [ ] PRG(Post-Redirect-Get) 패턴을 적용하여 중복 요청 문제를 해결할 수 있다.
- [ ] SQLAlchemy ORM을 사용하여 데이터베이스와 상호작용하는 CRUD 로직을 설계할 수 있다.

## 3장. 최종 결과물
- **홈 화면**: 서비스의 목적을 설명하고 주요 기능으로 이동하는 링크 제공.
- **단일 도메인 CRUD**: 사용자가 데이터를 등록, 목록 조회, 상세 조회, 수정, 삭제할 수 있는 기능.
- **PRG 패턴**: 데이터 변경(POST) 직후 리다이렉트(303)를 적용하여 새로고침 시 중복 요청 방지.
- **레이어 분리**: 라우터, 서비스, 저장소, 모델의 역할을 명확히 분리한 클린 아키텍처 구조.
- **SQLite 기반 저장**: 인메모리 방식이 아닌 SQLAlchemy와 SQLite를 연동하여 데이터 영속성 확보.

## 6장. 레이어드 아키텍처의 흐름
처음에는 왜 이렇게 코드를 쪼개는지 의문이 들 수 있다. 하지만 코드가 길어질수록 한 파일에 모든 로직이 있으면, 데이터베이스 구조를 바꿀 때 화면 출력 로직까지 다 뜯어고쳐야 하는 재앙이 발생한다.

```text
[Browser] ───(Request)───> [Router] ───> [Service] ───> [Repository] ───> [DB]
                                                                          │
[Browser] <──(HTML Render)── [Template] <─────────────────────────────────┘
```

| 레이어 | 역할 | 비유 |
| --- | --- | --- |
| **Router** | 요청을 받고 응답을 보냄 | 주문을 받는 웨이터 |
| **Service** | 비즈니스 로직 처리 | 요리를 만드는 요리사 |
| **Repository** | DB 직접 접근 | 식재료 창고 관리자 |

비전공자 관점에서는 "각자가 자기 할 일만 확실히 하면 된다"는 점을 기억하면 된다.

## 7장. PRG 패턴의 이해
데이터를 등록한 후 바로 결과를 보여주면, 사용자가 브라우저의 '새로고침'을 눌렀을 때 똑같은 데이터가 두 번 저장되는 참사가 발생한다.

처음에는 왜 리다이렉트를 하는지 이해하기 어려울 수 있다. 하지만 리다이렉트는 "이전 작업 끝났으니 이제 결과 페이지로 이동해!"라고 브라우저에게 명령을 내리는 것이다.

비유하자면 식당에서 주문(POST)을 완료한 후, 웨이터가 "주문 접수되었습니다"라고 말하고 영수증(GET)을 가져다주는 것과 같다. 영수증을 보고 새로고침을 해도 다시 주문이 들어가지 않는다.

## 8장. SQLAlchemy와 ORM
ORM은 파이썬 클래스를 데이터베이스 테이블처럼 다루게 해준다. SQL 문법을 몰라도 객체 지향 방식으로 데이터를 조작할 수 있다.

```python
# 예시: 데이터를 저장하는 코드
new_user = User(name="jhkr1")
db.add(new_user)
db.commit()
```

비유하자면 ORM은 **'번역기'**와 같다. 우리가 파이썬으로 말을 하면, ORM이 데이터베이스가 이해하는 SQL 언어로 번역해 준다.

비전공자 관점에서는 "데이터베이스와 대화할 때 SQL 언어를 직접 쓰지 않고 파이썬으로 소통한다"고 기억하면 된다.

## 9장. 의존성 주입 (Dependency Injection)
`Depends`를 사용하면 객체 생성을 직접 하지 않고 프레임워크에게 맡길 수 있다.

```python
def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

# 라우터에서 사용
@router.post("/items")
def create_item(db: Session = Depends(get_db)):
    ...
```

비유하자면 `Depends`는 **'필요할 때만 가져다 쓰는 공용 도구함'**과 같다. 내가 직접 도구를 만들 필요 없이, 필요할 때 요청하면 시스템이 도구를 가져다주고 사용 후에는 알아서 정리한다.

## 10장. Q&A
**Q1. 왜 라우터, 서비스, 저장소를 굳이 나누어야 하는가?**
A1. 비유하자면 식당에서 주문을 받는 사람(라우터), 요리를 하는 사람(서비스), 식재료를 관리하는 사람(저장소)을 나누는 것과 같다. 역할을 분리해야 요리법이 바뀌어도 주문 방식에 영향을 주지 않고, 식재료 관리 방식이 바뀌어도 요리 과정에 영향을 주지 않아 유지보수가 쉬워지기 때문이다.

**Q2. POST 다음에 왜 바로 렌더링하지 않고 Redirect를 하는가?**
A2. 사용자가 실수로 '새로고침' 버튼을 눌렀을 때, POST 요청이 다시 서버로 전달되어 데이터가 중복 생성되는 문제를 막기 위함이다. 리다이렉트를 하면 브라우저는 마지막으로 수행한 GET 요청을 다시 실행하므로 데이터 중복 문제가 발생하지 않는다.

**Q3. SQLAlchemy의 Session은 왜 Depends로 관리하는가?**
A3. 매번 DB 연결을 직접 생성하고 닫는 것은 번거롭고 실수하기 쉽다. FastAPI의 의존성 주입을 사용하면 요청이 시작될 때 세션을 열고, 요청이 끝날 때 자동으로 닫아주어 DB 연결 자원을 안전하게 관리할 수 있다.

**Q4. 비전공자도 이 구조를 이해할 수 있는가?**
A4. 물론이다. 모든 코드를 한 파일에 짜는 것보다, 역할별로 파일을 나누는 것이 레고 블록을 조립하는 것과 비슷하다는 점만 이해하면 된다. 나중에 특정 기능만 교체하고 싶을 때, 전체를 다시 만들지 않고 해당 블록만 바꾸면 되기 때문이다.
