이 문서는 FastAPI를 활용하여 웹 애플리케이션의 뼈대를 구축하는 방법을 다룬다. 단순히 기능을 구현하는 것을 넘어, 왜 코드를 나누고(Layered Architecture), 왜 PRG 패턴을 사용하며, 왜 ORM을 도입하는지 그 근본적인 이유를 파헤친다.

## 1장. 현대적 웹 프레임워크, FastAPI의 등장

FastAPI는 파이썬의 타입 힌트를 적극적으로 활용하여 빠르고 안전한 개발을 가능하게 하는 웹 프레임워크이다.

**비유하자면, FastAPI는 최신식 주방 시스템과 같다.** 요리사(개발자)가 재료(데이터)를 넣으면 정해진 규격(타입 힌트)에 따라 자동으로 조리 과정(검증 및 직렬화)을 관리해주기 때문에 실수를 줄이고 속도를 높일 수 있다.

처음에는 왜 이렇게 많은 제약(타입 힌트 등)을 강제하는지 의문이 들 수 있다. 하지만 협업 환경에서 데이터의 형태가 명확하지 않으면 버그가 발생하기 쉽다. FastAPI는 이 문제를 미리 방지한다.

| 특징 | 설명 | 이유 |
| --- | --- | --- |
| 성능 | 비동기 지원 | IO 작업이 많은 웹 서비스에서 병목 현상 최소화 |
| 생산성 | 자동 문서화 | Swagger UI를 통해 API 명세서 자동 생성 |
| 안정성 | 데이터 검증 | Pydantic을 통한 타입 기반의 자동 유효성 검사 |

**비전공자 관점에서는, FastAPI는 '입력된 데이터가 약속된 형식인지 꼼꼼하게 검사해주는 똑똑한 비서'라고 기억하면 된다.**

## 2장. 레이어 분리: 왜 역할을 나누는가?

소프트웨어 설계에서 가장 중요한 원칙 중 하나는 '관심사의 분리'이다.

**비유하자면, 식당의 운영과 같다.** 홀 직원(라우터)은 손님의 주문을 받고, 주방장(서비스)은 요리를 만들고, 식자재 창고 관리자(저장소)는 재료를 가져온다. 홀 직원이 직접 창고에 가서 재료를 가져오면 효율이 떨어지고 혼란이 생긴다.

```text
┌────────────────────────────────────────────────────────┐
│ [사용자(브라우저)]                                      │
└────────────┬───────────────────────────────────────────┘
             │ (요청)
┌────────────▼────────────┐
│ Router (입구/출구)       │ ◀─ 요청 수신 및 응답 반환
└────────────┬────────────┘
             │ (비즈니스 로직 호출)
┌────────────▼────────────┐
│ Service (핵심 로직)      │ ◀─ 데이터 가공 및 규칙 적용
└────────────┬────────────┘
             │ (데이터 접근)
┌────────────▼────────────┐
│ Repository (DB 연결)    │ ◀─ DB 쿼리 수행
└─────────────────────────┘
```

처음에는 그냥 한 파일에 다 쓰면 편하지 않나 의문이 들 수 있다. 하지만 기능이 조금만 커져도 코드는 '스파게티'처럼 꼬여버린다.

| 레이어 | 역할 | 핵심 책임 |
| --- | --- | --- |
| Router | 요청 수신 | HTTP 상태 코드 반환, 파라미터 파싱 |
| Service | 비즈니스 로직 | 도메인 규칙 검증, 데이터 계산 |
| Repository | 데이터 접근 | SQL 쿼리 실행, 객체 매핑 |

**비전공자 관점에서는, 각자 맡은 일만 잘하도록 역할을 나누어야 나중에 고치기 쉽다고 기억하면 된다.**

## 3장. 데이터베이스와의 대화: SQLAlchemy ORM

데이터베이스는 엑셀 파일과 비슷하지만, 코드로 다루기에는 복잡한 언어(SQL)가 필요하다.

**비유하자면, ORM은 외국어 통역사이다.** 우리는 파이썬 객체(메모)만 다루면 되지만, ORM은 이를 데이터베이스가 이해하는 SQL 언어로 번역해준다.

```python
# SQLAlchemy 모델 예시
from sqlalchemy import Column, Integer, String
from sqlalchemy.ext.declarative import declarative_base

Base = declarative_base()

class Memo(Base):
    __tablename__ = "memos"
    id = Column(Integer, primary_key=True)
    content = Column(String)
```

처음에는 직접 SQL을 짜는 게 빠르지 않나 의문이 들 수 있다. 하지만 데이터베이스 종류가 바뀌거나 구조가 복잡해지면 직접 짠 SQL은 유지보수가 불가능하다.

**비전공자 관점에서는, ORM은 '파이썬 코드를 데이터베이스 언어로 바꿔주는 번역기'라고 기억하면 된다.**

## 4장. PRG 패턴: 새로고침의 공포로부터 탈출하기

웹 브라우저에서 '새로고침' 버튼을 누르면 마지막으로 했던 행동이 반복된다. 만약 글을 쓴 직후에 새로고침을 하면 글이 두 번 등록될 위험이 있다.

**비유하자면, 카페에서 주문을 마친 뒤 영수증(GET)을 받는 과정과 같다.** 주문(POST)을 하고 나면 직원은 "주문이 완료되었습니다. 여기 영수증을 확인하세요"라고 안내(Redirect)한다. 이렇게 하면 고객이 다시 주문하는 실수를 막을 수 있다.

| 단계 | 동작 | 이유 |
| --- | --- | --- |
| POST | 데이터 저장 요청 | 상태 변경 발생 |
| Redirect | 다른 페이지로 이동 | POST 상태를 지움 |
| GET | 페이지 보여주기 | 안전한 조회 |

**비전공자 관점에서는, POST 뒤에는 반드시 페이지를 이동시켜서 중복 요청을 방지한다고 기억하면 된다.**

## 5장. 의존성 주입(Depends): 재료를 빌려오는 방법

FastAPI의 `Depends`는 필요한 도구나 데이터를 함수 호출 시점에 주입하는 기술이다.

**비유하자면, 요리사가 요리할 때 필요한 칼을 직접 만드는 게 아니라, '도구함'에서 빌려 쓰는 것과 같다.** 도구함(Depends)은 요리사가 요리에만 집중할 수 있게 도와준다.

```python
# DB 세션 주입 예시
def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

@router.get("/memos")
def list_memos(request: Request, db: Session = Depends(get_db)):
    # db를 사용하여 데이터 조회
    service = MemoService(db)
    return templates.TemplateResponse(request=request, name="list.html", context={"request": request, "memos": service.get_memos()})
```

처음에는 그냥 함수 내부에서 DB를 열면 되지 않나 의문이 들 수 있다. 하지만 이렇게 하면 DB 연결을 관리하기 어렵고 테스트하기 힘들다.

**비전공자 관점에서는, Depends는 '필요한 것을 미리 준비해두었다가 함수가 부를 때 가져다주는 시스템'이라고 기억하면 된다.**

## 6장. Jinja2와 SSR: 화면을 그리는 방법

SSR(Server Side Rendering)은 서버에서 HTML을 완성해서 브라우저로 보내는 방식이다.

**비유하자면, 밀키트(Jinja2)와 같다.** 재료는 그대로인데, 이름이나 내용물만 바꾸면 새로운 요리(HTML)가 뚝딱 만들어진다.

```html
<!-- templates/index.html -->
<h1>메모장</h1>
<ul>
    {% for memo in memos %}
        <li>{{ memo.content }}</li>
    {% endfor %}
</ul>
```

**비전공자 관점에서는, 템플릿 엔진은 '구멍 뚫린 양식에 이름만 바꿔서 서류를 찍어내는 기계'라고 기억하면 된다.**

## 7장. 요청과 응답의 흐름: 브라우저에서 DB까지

요청이 들어오면 서버는 다음과 같은 여행을 시작한다.

```text
[브라우저] ──(요청)──▶ [Router] ──▶ [Service] ──▶ [Repository] ──▶ [DB]
    ▲                                                              │
    └──────────────(응답)────────── [Template] ◀───────────────────┘
```

이 과정에서 각 레이어는 자기 할 일만 한다. 라우터는 요청을 해석하고, 서비스는 비즈니스 규칙을 확인하고, 레포지토리는 데이터를 가져온다.

**비전공자 관점에서는, 이 과정은 '주문서가 전달되고 요리가 완성되어 다시 전달되는 과정'이라고 기억하면 된다.**

## 11장. 예외 처리: 예상치 못한 상황 관리

웹 서비스는 항상 완벽하게 작동하지 않는다. 사용자가 없는 데이터를 찾거나, 잘못된 값을 입력할 수 있다.

**비유하자면, 식당에서 재료가 떨어졌을 때 손님에게 "죄송합니다"라고 안내하는 것과 같다.** 그냥 침묵하는 것보다 상황을 알리는 것이 중요하다.

처음에는 `try-except`를 모든 곳에 넣어야 하나 의문이 들 수 있다. 하지만 FastAPI의 `HTTPException`을 활용하면 깔끔하게 에러를 처리할 수 있다.

| 예외 상황 | 대응 방식 | 이유 |
| --- | --- | --- |
| 데이터 없음 | 404 Not Found | 리소스가 존재하지 않음을 명시 |
| 권한 부족 | 403 Forbidden | 보안 강화 |
| 잘못된 요청 | 422 Unprocessable Entity | 데이터 검증 실패 |

**비전공자 관점에서는, 예외 처리는 '문제가 생겼을 때 당황하지 않고 적절한 안내문을 띄우는 것'이라고 기억하면 된다.**

**비전공자 관점에서는, 테스트 코드는 '내 프로그램이 잘 작동하는지 자동으로 확인해주는 로봇'이라고 기억하면 된다.**

## 14장. 배포의 기초: 서버에 올리기

내 컴퓨터에서만 돌아가는 코드는 의미가 없다.

**비유하자면, 집에서 만든 요리를 손님에게 제공하기 위해 가게를 여는 것과 같다.**

| 단계 | 설명 |
| --- | --- |
| 패키징 | 필요한 라이브러리 정리 (requirements.txt) |
| 서버 설정 | Gunicorn/Uvicorn 설정 |
| 프로세스 관리 | Systemd나 Docker 활용 |

**비전공자 관점에서는, 배포는 '내 컴퓨터라는 울타리를 넘어 세상에 서비스를 공개하는 것'이라고 기억하면 된다.**

## Q&A

**Q1. 왜 굳이 서비스를 거쳐서 레포지토리로 가야 하나요?**
A1. 서비스는 비즈니스 로직(예: 메모 내용이 너무 길면 자르기)을 담당한다. 나중에 로직이 바뀌어도 레포지토리(DB 접근 방식)를 건드릴 필요가 없기 때문이다.

**Q2. RedirectResponse(status_code=303)를 꼭 써야 하나요?**
A2. 그렇다. 303 코드는 "POST 작업이 끝났으니, 이제 이 URL로 가서 GET으로 다시 확인해"라는 표준 약속이다. 새로고침 시 중복 요청을 방지하는 핵심이다.

**Q3. Depends는 어떻게 DB를 닫아주나요?**
A3. `yield` 키워드를 사용하기 때문이다. `yield` 이전 코드가 실행되고, 함수가 종료될 때 `finally` 블록이 실행되어 DB 세션을 안전하게 닫는다.

**Q4. Jinja2에서 데이터를 어떻게 넘기나요?**
A4. `TemplateResponse`를 사용할 때 `context` 인자에 딕셔너리 형태로 데이터를 전달하면 된다.

**Q5. SSR 방식의 장점은 무엇인가요?**
A5. 초기 로딩이 빠르고, 검색 엔진 최적화(SEO)에 유리하다. 또한, 클라이언트 복잡도가 낮아져 개발 속도가 빠르다.
