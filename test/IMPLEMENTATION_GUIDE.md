# [SPA 서비스 구현]으로 배우는 [React 핵심 데이터 흐름과 상태 관리]

이 문서는 React 기반의 단일 페이지 애플리케이션(SPA)을 구축하며 겪게 될 컴포넌트 설계, 상태 관리, 비동기 데이터 처리의 원리를 다룬다. 단순히 코드를 작성하는 것을 넘어, 왜 이러한 구조가 필요한지 근본적인 이유를 파악하는 것이 목표이다.

---

## 1장. SPA(Single Page Application)의 이해와 필요성

SPA는 서버에서 매번 새로운 HTML 페이지를 받아오는 대신, 최초 한 번만 전체 페이지를 불러오고 이후에는 필요한 데이터만 비동기로 받아와 화면의 일부분만 동적으로 교체하는 방식이다.

비유하자면, 전통적인 웹사이트는 매번 새로운 책을 새로 사서 읽는 것과 같다. 반면, SPA는 같은 책의 내용을 지우개로 지우고 새로운 글씨를 써넣는 방식이다. 페이지 전체를 새로고침하지 않으므로 사용자 경험(UX)이 훨씬 매끄럽다.

### SPA 동작 원리
```text
[브라우저] <---- (JSON 데이터만 요청) ---- [백엔드/Supabase]
    │                                          │
    └──── (JS가 화면의 일부를 재렌더링) ──────────┘
```

| 방식 | 특징 | 장점 | 단점 |
| --- | --- | --- | --- |
| MPA | 페이지 이동 시 새로고침 | 구현이 단순함 | 매번 리소스 재로딩 |
| SPA | JS로 DOM 조작 | 빠른 전환, 앱 같은 느낌 | 초기 로딩 속도, SEO |

비전공자 관점에서는 "전체 페이지를 갈아엎지 않고, 필요한 부분만 쏙쏙 고쳐 쓰는 방식"이라고 기억하면 된다.

## 2장. 컴포넌트의 분리: 왜 재사용인가?

컴포넌트는 UI의 최소 단위이다. 처음에는 모든 코드를 한 파일에 작성하고 싶을 것이다. 하지만 기능이 늘어날수록 코드는 '스파게티'처럼 엉키게 된다.

비유하자면, 레고 블록과 같다. 레고로 성을 만들 때 창문, 문, 벽돌을 미리 만들어두면 나중에 다른 성을 만들 때도 그대로 가져다 쓸 수 있다. 컴포넌트도 이와 같다.

### 컴포넌트 구조화 예시
```text
src/
├── components/     # 재사용 가능한 UI 블록 (Button, Input)
├── pages/          # 라우트에 대응하는 큰 화면 (Home, Login)
└── hooks/          # 상태 로직 (useAuth, useItems)
```

처음에는 왜 이렇게 폴더를 나누는지 의문이 들 수 있다. 하지만 나중에 `Button` 디자인을 수정해야 할 때, 10개의 페이지를 다 뒤지는 대신 `components/Button.jsx` 하나만 수정하면 된다는 사실을 깨닫게 된다.

비전공자 관점에서는 "레고 블록처럼 부품화해서 관리해야 나중에 수정이 쉽다"고 기억하면 된다.

## 3장. 라우팅: 페이지 이동의 마법

SPA에서 주소창의 URL이 바뀌어도 실제 서버에 페이지를 요청하지 않는다. `React Router` 같은 라이브러리가 URL을 감지하고, 그에 맞는 컴포넌트를 브라우저에 렌더링할 뿐이다.

비유하자면, 도서관의 '안내판'과 같다. 안내판은 바뀌지 않지만, 그 위에 놓이는 책(컴포넌트)만 계속 바뀐다.

### 라우팅 흐름
```text
/login  ──> [Login 컴포넌트]
/items  ──> [ItemList 컴포넌트]
/items/:id ──> [ItemDetail 컴포넌트]
```

| 설정 | 역할 |
| --- | --- |
| Route | URL과 컴포넌트 매칭 |
| Link | 페이지 이동 (새로고침 방지) |
| useParams | URL 파라미터(id 등) 추출 |

비전공자 관점에서는 "주소창과 화면을 연결하는 다리 역할"이라고 기억하면 된다.

## 4장. 상태(State)와 데이터의 흐름

React에서 상태는 '변화하는 데이터'이다. 컴포넌트는 상태가 변할 때마다 스스로를 다시 그린다(리렌더링).

비유하자면, 전광판의 숫자와 같다. 버튼을 누르면(이벤트) 전광판의 숫자(상태)가 바뀌고, 그에 따라 화면(UI)이 즉시 업데이트된다.

### 상태의 단방향 흐름
```text
[부모 컴포넌트] (상태 보유)
      │
      ▼ (props 전달)
[자식 컴포넌트] (화면 표시)
```

처음에는 왜 상태를 부모에 두어야 하는지 의문이 들 수 있다. 하지만 형제 컴포넌트끼리 데이터를 공유해야 할 때, 공통 부모가 데이터를 가지고 있어야 전달이 가능하기 때문이다.

비전공자 관점에서는 "데이터는 위에서 아래로 흐르고, 상태가 바뀌면 화면은 자동으로 업데이트된다"고 기억하면 된다.

## 5장. 제어 컴포넌트(Controlled Input)와 폼 UX

사용자가 입력하는 폼은 React의 상태로 관리해야 한다. 이를 '제어 컴포넌트'라고 부른다.

비유하자면, 실시간으로 받아쓰기를 하는 학생과 같다. 사용자가 글자를 한 자 칠 때마다(onChange), 그 값을 상태에 즉시 반영한다.

```javascript
const [value, setValue] = useState("");
<input value={value} onChange={(e) => setValue(e.target.value)} />
```

| 항목 | 의미 |
| --- | --- |
| Controlled | React 상태가 값을 주도함 |
| Uncontrolled | DOM이 값을 주도함 |

비전공자 관점에서는 "입력창의 값을 항상 React가 감시하고 있어야 에러 메시지나 제출 제어가 쉽다"고 기억하면 된다.

## 6장. useEffect와 비동기 데이터의 생애주기

데이터를 서버(Supabase)에서 가져올 때 `useEffect`를 사용한다. 이는 컴포넌트가 화면에 나타날 때 딱 한 번 실행되게 하거나, 특정 상태가 변할 때마다 실행되게 한다.

비유하자면, 요리사가 식당 문을 열자마자(마운트) 재료를 주문하는 것과 같다.

```javascript
useEffect(() => {
  fetchData();
}, []); // 빈 배열은 '처음 한 번만'을 의미
```

처음에는 왜 `useEffect`를 쓰는지 의문이 들 수 있다. 하지만 비동기 데이터는 시간이 걸리기 때문에, 컴포넌트 렌더링과 분리해서 처리해야 앱이 멈추지 않는다.

비전공자 관점에서는 "화면이 그려진 후 서버에 데이터를 요청하는 타이밍을 맞추는 도구"라고 기억하면 된다.

---

## 7장. 로딩, 에러, 빈 상태의 UI 패턴

사용자는 데이터가 불러와지는 동안 기다려야 한다. 이때 로딩, 에러, 빈 상태를 처리하지 않으면 앱이 고장 난 것처럼 보인다.

비유하자면, 식당에서 음식이 나오기 전까지 '요리 중'이라는 팻말을 두는 것과 같다.

### 상태별 UI 흐름
```text
[요청 시작] ──> [Loading]
[요청 성공] ──> [데이터 표시]
[요청 실패] ──> [Error 메시지]
[데이터 없음] ──> [Empty 상태]
```

비전공자 관점에서는 "사용자에게 지금 무슨 일이 일어나고 있는지 친절하게 알려주는 UI 배려"라고 기억하면 된다.

## 8장. 커스텀 훅(Custom Hook)으로 로직 분리

컴포넌트 안에 데이터 가져오는 로직이 길어지면 읽기 힘들다. 이때 로직만 쏙 뽑아낸 것을 커스텀 훅이라고 한다.

비유하자면, 복잡한 커피 머신 조작법을 '버튼 하나'로 단순화하는 것과 같다.

```javascript
// useItems.js
export function useItems() {
  const [items, setItems] = useState([]);
  // ... 데이터 가져오는 로직 ...
  return items;
}
```

비전공자 관점에서는 "복잡한 기능을 묶어서 재사용 가능하게 만드는 함수"라고 기억하면 된다.

## 9장. CRUD: 데이터의 생성, 조회, 수정, 삭제

CRUD는 서비스의 핵심이다. Supabase를 사용하면 직접 백엔드를 만들지 않아도 데이터를 관리할 수 있다.

| 작업 | 의미 |
| --- | --- |
| Create | 데이터 추가 (INSERT) |
| Read | 데이터 조회 (SELECT) |
| Update | 데이터 수정 (UPDATE) |
| Delete | 데이터 삭제 (DELETE) |

비전공자 관점에서는 "데이터를 다루는 4가지 필수 동작"이라고 기억하면 된다.

## 10장. 배포와 환경변수 관리

마지막으로 만든 앱을 세상에 공개하는 단계다. 이때 API Key는 매우 중요하다.

비유하자면, 집 열쇠를 길가에 떨어뜨리는 것과 같다. `.env` 파일은 열쇠를 보관하는 금고이고, `.gitignore`는 그 금고를 훔쳐가지 못하게 하는 방어막이다.

비전공자 관점에서는 "보안 정보를 코드에 직접 쓰지 말고, 배포 서비스의 설정창에 입력한다"고 기억하면 된다.

## Q&A 섹션

**Q1. 왜 상태를 부모 컴포넌트에 두어야 하나요?**
A1. 여러 자식 컴포넌트가 같은 데이터를 공유해야 할 때, 상태를 가장 가까운 공통 조상에 두어야 데이터 일관성을 유지할 수 있기 때문이다. 이를 '상태 끌어올리기'라고 한다.

**Q2. `useEffect`의 의존성 배열(Dependency Array)이 왜 중요한가요?**
A2. 배열에 넣은 값이 변할 때만 `useEffect`가 재실행된다. 이를 생략하면 매번 불필요한 API 요청이 발생하여 서버 비용이 증가하고 앱 성능이 저하된다.

**Q3. 컴포넌트를 8개 이상 나누라는 이유는 무엇인가요?**
A3. 재사용성을 극대화하고, 하나의 컴포넌트가 너무 많은 책임을 갖지 않게(단일 책임 원칙) 하기 위해서다. 페이지마다 중복되는 UI를 컴포넌트로 분리하면 유지보수가 획기적으로 쉬워진다.

**Q4. 왜 굳이 Supabase 같은 백엔드 서비스를 쓰나요?**
A4. 프론트엔드 개발자가 서버 구현에 드는 시간을 줄이고, React의 데이터 흐름과 UI/UX 완성도에 집중할 수 있게 해주기 때문이다.

**Q5. 데이터가 없을 때와 에러가 났을 때를 구분해야 하나요?**
A5. 그렇다. '데이터가 없음'은 정상적인 상황(빈 리스트)이고, '에러'는 비정상적인 상황(네트워크 끊김)이다. 사용자에게는 각각 다른 메시지를 보여주어야 혼란을 방지할 수 있다.
