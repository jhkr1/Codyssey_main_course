## Case 1: 비동기 데이터 요청 시 발생하는 "무한 렌더링 루프"

### 1. Description (현상 설명)
데이터를 가져오기 위해 `useEffect` 내에서 상태를 업데이트하는 함수를 호출했는데, 브라우저가 응답하지 않고 멈추거나 콘솔에 네트워크 요청이 수백 번씩 찍히는 현상이다. 페이지에 진입하자마자 발생한다.

### 2. Evidence & Logs (증거 자료)
```javascript
useEffect(() => {
  // 데이터를 불러온 뒤 상태 업데이트
  fetchItems().then(data => setItems(data));
}, [items]); // 의존성 배열에 상태를 직접 넣음
```

### 3. Root Cause Analysis (원인 분석)
비유하자면, "거울을 마주 보고 서 있는 거울"과 같다. 상태를 업데이트하면 컴포넌트가 다시 그려지고, 다시 그려진 컴포넌트가 `useEffect`를 실행하며, 다시 상태를 업데이트하는 악순환이다.

| 가설 | 가능성 | 검증 방법 |
| --- | --- | --- |
| 의존성 배열에 상태 변수가 포함됨 | 높음 | 의존성 배열에서 해당 상태를 제거 |
| 무한 루프 감지 | 높음 | 콘솔 로그를 찍어 렌더링 횟수 확인 |

### 4. Workaround & Verification (조치 및 검증)
| 구분 | 내용 |
| --- | --- |
| Before | `[items]`를 의존성 배열에 명시하여 상태 변경마다 재실행 |
| After | `[]`를 사용하여 컴포넌트 마운트 시 1회만 실행 |

### 5. 재발 방지
`useEffect`의 의존성 배열은 "이 값이 바뀔 때만 다시 실행해라"라는 약속이다. 데이터 로딩처럼 초기 1회만 필요한 작업은 반드시 빈 배열 `[]`을 사용한다.

## Case 2: 폼 제출 시 이전 데이터가 남아있는 문제

### 1. Description (현상 설명)
게시물을 등록하고 목록으로 돌아왔는데, 방금 작성한 내용이 폼에 그대로 남아있다. 혹은 수정 화면에서 이전 데이터를 불러온 뒤, 다른 데이터로 이동해도 이전 데이터가 잔상처럼 남아있는 현상이다.

### 2. Evidence & Logs (증거 자료)
```javascript
const [formData, setFormData] = useState({ title: '', content: '' });

const handleSubmit = async () => {
  await postData(formData);
  navigate('/items');
  // 여기서 formData를 초기화하지 않음
};
```

### 3. Root Cause Analysis (원인 분석)
비유하자면, 식당에서 손님이 나가고 테이블을 닦지 않은 것과 같다. React의 상태는 컴포넌트가 사라지기 전까지 메모리에 유지되기 때문에 명시적인 초기화가 필요하다.

| 가설 | 가능성 | 검증 방법 |
| --- | --- | --- |
| 상태 초기화 로직 부재 | 높음 | 제출 성공 후 상태 설정 함수 호출 확인 |
| 컴포넌트 생명주기 오해 | 중간 | 페이지 이동 시 컴포넌트 언마운트 여부 확인 |

### 4. Workaround & Verification (조치 및 검증)
| 구분 | 내용 |
| --- | --- |
| Before | 제출 성공 후 `navigate`만 실행 |
| After | 제출 성공 후 `setFormData`로 기본값 재설정 후 이동 |

### 5. 재발 방지
입력 폼은 "항상 깨끗한 상태"를 유지해야 한다. `useEffect`의 `cleanup function`을 활용하거나, 제출 성공 직후 상태를 초기화하는 패턴을 정례화한다.

## Case 3: 환경변수(.env)가 배포 환경에서 적용되지 않음

### 1. Description (현상 설명)
로컬에서는 Supabase 연동이 잘 되는데, Vercel에 배포만 하면 "API Key를 찾을 수 없다"는 에러가 발생하며 데이터가 불러와지지 않는다.

### 2. Evidence & Logs (증거 자료)
```text
Error: Supabase client initialization failed. 
Missing SUPABASE_URL or SUPABASE_ANON_KEY.
```

### 3. Root Cause Analysis (원인 분석)
비유하자면, 여행을 가면서 가방(코드)만 챙기고 여권(환경변수)을 집에 두고 온 것과 같다. `.env` 파일은 보안상 `.gitignore`에 포함되므로 서버에 올라가지 않는다.

| 가설 | 가능성 | 검증 방법 |
| --- | --- | --- |
| .env가 깃에 포함됨 | 낮음 | .gitignore 파일 확인 |
| 배포 플랫폼 환경변수 미설정 | 매우 높음 | Vercel 대시보드 Settings > Environment Variables 확인 |

### 4. Workaround & Verification (조치 및 검증)
| 구분 | 내용 |
| --- | --- |
| Before | 로컬 .env 파일에만 의존 |
| After | 배포 플랫폼 대시보드에 동일한 Key-Value 쌍을 추가 |

### 5. 재발 방지
배포 전, 로컬에 있는 `.env` 파일의 키들을 배포 플랫폼의 환경변수 설정창에 옮겨 적는 것을 배포 체크리스트의 1번 항목으로 지정한다.

## Q&A (성찰 질문)

**Q1. 왜 상태를 `useState`에 담아야 하는가?**
A1. 일반 변수는 값이 바뀌어도 React가 화면을 다시 그려야 할지 모르기 때문이다. `useState`는 "이 값이 바뀌면 화면을 다시 그려라"라는 신호를 React 엔진에 보내는 장치이다.

**Q2. 컴포넌트를 쪼개는 기준은 무엇인가?**
A2. "재사용성"과 "역할의 단일화"이다. 한 컴포넌트가 너무 많은 일을 하면 유지보수가 어렵다. 비유하자면, 요리사는 재료 손질만 하고, 서빙은 서빙 담당자가 하는 것이 효율적인 것과 같다.

**Q3. 비전공자 관점에서는 무엇을 기억하면 되는가?**
A3. React는 "상태(데이터)가 바뀌면 화면이 자동으로 바뀐다"는 점만 기억하면 된다. 개발자는 화면을 직접 수정하는 것이 아니라, 데이터만 관리하면 React가 알아서 화면을 수정해준다.

**Q4. useEffect를 사용할 때 가장 주의할 점은 무엇인가?**
A4. 의존성 배열이다. 의존성 배열을 생략하면 매 렌더링마다 실행되어 성능을 저하시키고, 잘못 설정하면 무한 루프의 늪에 빠지게 된다.

**Q5. 왜 Supabase 같은 백엔드 서비스를 사용하는가?**
A5. 우리가 집중해야 할 것은 "데이터를 어떻게 화면에 보여줄 것인가"라는 프론트엔드의 고민이기 때문이다. 서버 구축이라는 복잡한 과정을 외부 서비스에 위임하여 학습 효율을 높이는 것이다.
